## 1. State of agentic AI, mid-2026

Production multi-agent systems still default to a **central orchestrator-worker pattern** (AutoGen, LangGraph, OpenAI Swarm) — a single controller owning the workflow graph, favored when workflows are complex but required autonomy is low (https://www.langchain.com/langgraph, https://github.com/openai/swarm, https://www.microsoft.com/en-us/research/publication/autogen-enabling-next-gen-llm-applications-via-multi-agent-conversation-framework/). MapReduce-style and hierarchical orchestration are the standard scaling pattern once single-orchestrator throughput bottlenecks (https://www.youtube.com/watch?v=l_i7icCA56c, https://www.youtube.com/watch?v=2czYyrTzILg). AgentFlow (2026) pushes further, formalizing harnesses as a typed graph DSL with a feedback-driven outer loop that rewrites the harness itself at runtime based on observed failures (https://arxiv.org/html/2604.20801v1) — orchestration structure is becoming an optimization target, not just a design-time choice.

Verification inside these systems leans on producer-reviewer/critic loops (native in AutoGen) and LLM-as-judge panels, which reach ~80% agreement with human evaluators at ~500x lower cost (LangChain 2025 State of AI Agents survey) but share bias with the judged model and miss tool-call-level errors (https://vadim.blog/llm-as-judge/, https://www.langchain.com/state-of-agent-engineering). Human-in-the-loop is treated as a first-class workflow node (pause only the risky branch, not the whole pipeline) for high-uncertainty decisions (https://orkes.io/blog/human-in-the-loop). Reliability engineering borrows directly from distributed systems: circuit breakers that fail fast after repeated agent-call failures, and saga/compensation patterns where every agent exposes execute + compensate so the orchestrator can roll back partial work (https://www.youtube.com/watch?v=2czYyrTzILg).

Self-correction is moving past single-loop Reflexion (2023): RR-MP (2025) splits reactive (exploration) and reflection (critique) into separate agents over multiple parallel reasoning paths specifically to escape "death-of-thought" loops that trap single-path agents (https://arxiv.org/html/2501.00430v1). A 2026 dynamic test-time-compute paper shows always-planning (ReAct-style) actively *degrades* long-horizon performance while never-planning keeps agents shallow — the fix is a two-stage SFT+RL pipeline that teaches agents when to invest in planning, further steerable by human-written plans (https://openreview.net/forum?id=mBxFCTlFmW).

Memory architecture is tiering: MemoryOS (2025) organizes short/mid/long-term memory with heat-based eviction, delivering +49.1% F1 / +46.2% BLEU-1 over baselines on LoCoMo with GPT-4o-mini (https://arxiv.org/html/2506.06326v1); Mem^p (2025) adds a dedicated procedural-memory layer for reusable task recipes, distinct from episodic/semantic memory (https://arxiv.org/html/2508.06433v2). Anthropic names compaction (summarizing/distilling history) as the first practical lever against long-horizon incoherence, alongside entity-centric memory and task-specific templates (https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents).

**The headline practitioner data** (LangChain "State of Agent Engineering 2026," 1,300+ professionals): 57.3% already run agents in production, 30.4% actively building; **quality (hallucination, consistency) is now the #1 blocker (~1/3 of respondents), having overtaken cost.** 89% have some observability, but only 52% have any evaluation framework at all — a large observability-vs-evaluation gap (https://www.langchain.com/state-of-agent-engineering). Context rot (gradual degradation from overload/staleness/crude truncation) is named as a top failure mode (https://arxiv.org/abs/2310.08560). Tool-call hallucination and cross-step error compounding are recurring, worsened by absent data-contract validation between steps (https://mlflow.org/articles/building-production-ready-ai-agents-in-2026/). An industry estimate projects ~40% of agentic AI projects canceled by 2027, blamed on unclear success metrics and inadequate evaluation pipelines (https://blaxel.ai/blog/how-to-deploy-ai-agents).

## 2. Grounding / provenance science — what products get wrong

The central finding: **citation correctness is not citation faithfulness.** A citation can point to a real, topically relevant document and still fail a causal faithfulness test (the doc didn't actually influence the generated claim) — up to **57%** of citations in attributed RAG answers fail this test due to "post-rationalization," where the model answers from parametric memory and attaches a plausible-looking source after the fact (https://aclanthology.org/2025.clicit-1.23.pdf).

Detection ceilings are low across the board. On RAGTruth (~18K annotated RAG responses), no detector — including GPT-4-based prompted judges — achieves both precision and recall above 50% (https://aclanthology.org/2024.acl-long.585/). Self-consistency (resampling and checking agreement) is a weak signal because models can be confidently, consistently wrong when they hold a false prior (https://arxiv.org/html/2311.01740v2). Semantic entropy (clustering sampled answers by meaning, computing entropy over clusters) is the leading calibration technique and correlates better with correctness than token probability, but still fails on systematically confident wrong answers (https://arxiv.org/html/2406.13663v1, Nature 2024). Vectara's HHEM v2, a dedicated hallucination-detection model, hits ~73% accuracy on AggreFact's SOTA subset — beating an LLM judge by ~10 points at far lower cost/latency, but still meaning roughly 1 in 4 classifications is wrong (https://www.vectara.com/blog/hhem-v2-a-new-and-improved-factual-consistency-scoring-model). Best-in-class detectors top out at ~70.2% (AggreFact) / ~75.8% (SummaC) accuracy — mechanical hallucination gating is decision-support today, not autonomous fact-checking.

Mechanical (non-self-report) citation verification does exist but is concentrated in research prototypes: Mirage identifies context-sensitive answer tokens via saliency analysis and attributes them to the retrieved docs that causally influenced them, sidestepping the non-existent-source and post-hoc-matching failure modes of self-citation (https://arxiv.org/abs/2511.16198). SemanticCite runs full-text retrieval within cited sources and classifies each claim-source pair as Supported/Partially Supported/Unsupported/Uncertain against a public 1,000+ citation benchmark, and shows fine-tuned small models matching large commercial systems on this task (https://dl.acm.org/doi/10.1145/3767695.3769505). VeriCite is a similar explicit post-generation verification layer.

Notably, **Anthropic's own Claude Citations API only guarantees pointer correctness** — cited spans are structurally real and present in the source document — not semantic faithfulness; it solves "hallucinated citation," not "citation doesn't actually support the claim" (https://platform.claude.com/docs/en/build-with-claude/citations). Mainstream consumer products (Perplexity, Gemini AI Overviews, Bing Copilot, ChatGPT search) display citations as retrieval pointers with instructions to "verify the source," not claim-level entailment checks (https://www.perplexity.ai/hub/products/search). Google's own enterprise guidance for staff using Gemini Search grounding explicitly says to open and manually verify every citation and re-prompt for a primary source if one resolves to a secondary — the vendor's own operational posture is "trust but verify," not "trust" (https://stanford.service-now.com/services?id=kb_article&number=KB00020824).

**What this means for products claiming "verified" or "grounded" answers:** the term needs to disclose *which* guarantee is being made — pointer-only (cited span is real), entailment-checked (a model scored support), or causally-attributed (saliency-traced influence) — because these are meaningfully different strengths of claim, and today's best mechanical checks still leave a 25-30%+ error rate.

## 3. Hierarchical knowledge (RAPTOR lineage) — best practices

RAPTOR (2024) established the baseline: recursive embed→cluster→abstractive-summarize, building a tree retrieved via a mix of root/parent (thematic) and leaf (detailed) nodes (https://arxiv.org/abs/2401.18059). 2025-2026 successors converge on one fix to RAPTOR's core weakness (pure semantic clustering loses document/code structure): **anchor hierarchy construction to actual structure (AST/LSP/document sections), not embedding clusters.**

- Psi-RAG (2026): adaptive merge/collapse tree + multi-granular retrieval agent; beats RAPTOR by 25.9% F1 and HippoRAG2 (a strong graph-RAG baseline) by 7.4% F1 on cross-document multi-hop QA (https://arxiv.org/abs/2605.00529).
- KohakuRAG (Mar 2026): explicit 4-level tree (doc→section→paragraph→sentence), bottom-up embedding aggregation, LLM query planner with cross-query reranking, abstention-aware ensemble voting; open source (https://arxiv.org/abs/2603.07612, https://github.com/Kohaku-Lab/KohakuRAG).
- MCHRAG: Multi-Centroid Routing Tree purpose-built for streaming/incremental updates, avoiding full re-clustering (https://dl.acm.org/doi/10.1145/3805622.3810580).
- Microsoft's LazyGraphRAG (Nov 2024) is a philosophical reversal: skip upfront graph/summary construction entirely, defer extraction and summarization to query time, cutting indexing cost near zero while matching or beating specialized query mechanisms (https://www.microsoft.com/en-us/research/blog/lazygraphrag-setting-a-new-standard-for-quality-and-cost/). GraphRAG's broader ecosystem now includes Claimify (claim extraction), BenchmarkQED (eval), and VeriTrail (provenance/hallucination tracing) (https://www.microsoft.com/en-us/research/project/graphrag/).

**Tree vs. graph is workload-driven, not a universal winner:** a 2025 benchmark across Fast-GraphRAG, LightRAG, HippoRAG2, StructRAG, KAG shows graphs win clearly on multi-hop/relational reasoning and fact retrieval; trees/flat approaches are cheaper and sufficient for narrative/hierarchical summarization (https://arxiv.org/abs/2506.05690).

For **codebases specifically**, structure-first parsing consistently beats embedding-clustering, replicated across four independent 2025-2026 papers: Meta-RAG builds AST-matched per-file summaries, ~80% size reduction, top-down file→class→function retrieval, incremental per-change updates, best bug-localization on SWE-bench Lite (https://arxiv.org/html/2508.02611v1); HCAG recursively parses bottom-up (leaf files→directories→repo root) with a depth-cutoff/placeholder pattern for lazy expansion of deep subtrees (https://arxiv.org/html/2603.20299v1); Agent4cs uses multi-agent bottom-up summarization (summarizer + keyword-extractor + QA/refinement agents), +8% folder↔subfolder coherence over single-pass prompting (https://arxiv.org/pdf/2607.01425v1.pdf); HCGS does bottom-up traversal of an LSP-derived code graph, up to 82% relative top-1 precision improvement (https://arxiv.org/html/2504.08975v1). Commercial productization already exists: Pharaoh (Tree-sitter→Neo4j knowledge graph exposed via MCP), Greptile (pre-indexed whole-repo graph), Sourcegraph (indexed cross-repo symbol search as MCP context) (https://pharaoh.so/blog/codebase-intelligence-tool-comparison-2026/).

Incremental maintenance is a solved, documented pattern: content-hash each file, skip unchanged, delete+re-embed only changed chunks, cutting re-index time from hours to seconds for commit-sized diffs (https://helain-zimmermann.com/blog/rag-for-code-retrieval-over-codebases).

## 4. Competitive landscape + THE GAP

**DeepWiki (Cognition/Devin)**, launched May 2025, is the free public benchmark: swap `github.com`→`deepwiki.com` on any repo for an auto-generated wiki + Q&A; indexed 50,000+ repos at launch (https://cognition.com/blog/deepwiki). It has **documented, repeated, embarrassing production hallucinations**: a maintainer called it "hallucinating pretty convincingly" and said confirming its answers was slower than reading the code (https://news.ycombinator.com/item?id=45002092); it misidentified LibreOffice's primary build system; a November 2025 maintainer post titled "DeepWiki and the loss of control" called it "a fractal of misinformation and abusive design" after it hallucinated an unpublished/broken VS Code extension as "the main way to use" the project — and a Cognition-affiliated commenter defended the AI over the maintainer's correction (https://blopker.com/writing/12-deepwiki/). This is a **reputational** failure mode as much as a technical one: DeepWiki republishes wrong claims about a project with no correction path, and appears in search alongside official docs. Private-repo access requires paid Devin (Max ~$200/mo+seats), cloud-only, no self-hosted option (https://devin.ai/pricing/).

**Greptile** builds a whole-repo graph index plus an agent swarm for review, benchmarked at 82% bug-catch rate vs. CodeRabbit's 44% — but with 11 false positives per run vs. CodeRabbit's 2, a real precision/recall inversion between the two leading review products (dev.to benchmark, June 2026). Pricing instability (flat $30/seat → $30/seat+$1/review overage, changed March 2026) triggered public backlash: surprise bills, contested post-cancellation charges, teams building in-house replacements (multiple r/codereview threads, 2026). Self-hosting is Enterprise-only, not self-serve.

**Sourcegraph** is the outlier on citation trust: Cody/Deep Search has a dedicated "Citations" tab with numbered, deduped citations and inline code snippets tying each claim to specific files/lines — the only vendor treating verifiable citation as a first-class UI requirement (https://sourcegraph.com/docs/technical-changelog). It's also the only major vendor with a genuine on-prem story. But Enterprise starts ~$16,000 — not a self-serve local product.

**mutable.ai** is confirmed dead — a credible, well-funded early entrant in this exact category went dark by end of 2024 with no formal shutdown announcement; its CEO quietly joined Google (https://pitchbook.com/profiles/company/226304-92). This is a real signal about category difficulty, not just a generic startup-failure story.

Privacy-only tools (Understand/SciTools: fully local static analysis, zero generative Q&A) and local-LLM-capable-but-unpackaged tools (Continue.dev: documented self-hosting of any OpenAI-compatible model, but a bring-your-own-LLM chat extension with no indexing/wiki product) exist at the edges but don't combine.

**THE GAP, confirmed not speculative:** No product combines (a) fully local/air-gapped-by-default deployment with (b) a packaged generative wiki/Q&A layer with (c) verifiable line-level citation enforced as a hard constraint. Understand has (a) but not (b)/(c). DeepWiki/Devin/Greptile/Cursor have (b) but not (a), and have documented, repeated (c) failures. Sourcegraph has the strongest (c) but only as a $16k+ enterprise SKU, not (a). The wedge is combining Understand's privacy posture + Continue.dev's local-LLM flexibility + Sourcegraph's citation discipline — none of which currently ship together.

## 5. Computational methods that make corpus summarization cheap and reliable

**Map-reduce is the throughput-preferred workflow pattern** for long-document/corpus summarization: chunk-level summarization is embarrassingly parallel and can run on cheap/local models; only the reduce/aggregation step (much smaller token volume) needs a stronger model or verification pass, so cost scales at the cheap local-model rate with verification cost concentrated at the aggregation layer (https://cloud.google.com/blog/products/ai-machine-learning/long-document-summarization-with-workflows-and-gemini-models). Iterative refinement is more coherent but sequential/slower — reserve for cases needing tight narrative continuity, not corpus scale.

**Test-time compute can substitute for parameter count.** Snell et al. show compute-optimal allocation (verifier-guided search + adaptive sampling, scaled by per-prompt difficulty) improves efficiency >4x over naive best-of-N, and at matched FLOPs a model 14x smaller can beat a larger one when paired with verification (https://arxiv.org/abs/2408.03314). This directly argues against uniformly running the biggest model on every chunk — allocate extra sampling/verification only where a segment trips an uncertainty threshold.

**Verification layer:** Process Reward Models (PRMs) score intermediate steps/claims, not just final output, and are a mature 2025-2026 pattern with an existing off-the-shelf zoo (no need to train from scratch) (https://arxiv.org/html/2510.08049v3, https://github.com/RyanLiu112/Awesome-Process-Reward-Models). Directly portable to summarization: score each summary claim for source-traceability, prune hallucinated candidates. Self-consistency (sample N, keep highest-agreement) delivers large, cheap gains on reasoning tasks (+17.9pp GSM8K) and generalizes to "sample N summaries, keep highest cross-sample factual overlap" (https://arxiv.org/abs/2203.11171). Semantic entropy is the model-agnostic gate for "should I re-generate this" (https://www.nature.com/articles/s41586-024-07421-0).

**Critical caution: don't trust an LLM judge alone.** InstruSum found persistent factual errors/omissions across 5 top LLM summarization systems, and across 40 different LLM-judge evaluation methods (11 models × 4 schemes) *none* achieved strong human alignment (https://aclanthology.org/2024.findings-naacl.280/). Pair any LLM-judge pass with PRM/semantic-entropy structural checks or human-audited samples.

**Local-model verdict:** Phi-4 (14B), trained data-centrically on a synthetic reasoning/education-scored curriculum, beats its own teacher GPT-4o on GPQA/MATH and matches/exceeds Llama-3.1-405B on reasoning benchmarks (https://arxiv.org/html/2412.08905v1) — the strongest concrete evidence a 7-14B local model is a credible general-summarization base in 2026, *provided it's paired with verification*. Qwen2.5-Coder (32B reportedly GPT-4o-competitive on code; 7B/14B run on commodity single-GPU) is the concrete code-specialist choice, with routing to it for code segments vs. a general model for prose (https://ollama.com/library/qwen2.5-coder). Use a code-generation-derived embedding model (e.g. jina-code-embeddings) rather than a generic text embedder for indexing code (https://arxiv.org/abs/2508.21290), validated against MTEB before committing (https://huggingface.co/spaces/mteb/leaderboard).

**Important gap in the evidence:** no direct summarization-quality benchmark for 7-14B local models vs. GPT-4-class models exists in this research pull. Phi-4/Qwen2.5-Coder numbers are reasoning/code-benchmark proxies, not summarization-specific. This is the single most decision-relevant number for a build and must be measured empirically against a human-labeled sample of the actual target corpus, not assumed from adjacent benchmarks (echoes InstruSum's caution about trusting either generation or judge quality without ground truth).

## 6. PRODUCT IMPLICATIONS — for a local-first repo/docs-to-verified-knowledge-tree tool

**What the research supports building:**

1. **Local-first-by-default deployment is a genuine, unclaimed wedge.** No competitor combines local/air-gapped deployment with a packaged generative Q&A layer (Section 4). This is the single strongest go/no-go signal in the whole research set — it's not "differentiated," it's a category gap confirmed by absence across every named competitor.
2. **Structure-anchored hierarchy, not RAPTOR-style pure clustering.** Every 2025-2026 codebase paper (Meta-RAG, HCAG, Agent4cs, HCGS, KohakuRAG) converges on parsing AST/LSP/document structure first, then summarizing bottom-up (function→file→module→subsystem→repo). This is now consensus, not a contested design choice (Section 3).
3. **Map-reduce summarization architecture**, chunk-level work on cheap local models (Phi-4-class for prose, Qwen2.5-Coder-class for code), verification concentrated at the reduce/aggregation step — this is the mechanism that makes local-only economically viable at repo scale (Section 5).
4. **Citation must disclose its verification tier, not claim uniform authority.** Given Anthropic's own Citations API only guarantees pointer-correctness, and mechanical entailment checks (HHEM, SemanticCite) cap out around 70-76% accuracy, the product's citation UI should show *what kind* of guarantee each citation carries — e.g., "pointer verified" (span exists in source) vs. "entailment scored" (a PRM/detector checked support) vs. "unverified" — rather than presenting all citations with equal visual authority (Section 2, Section 4's Sourcegraph example).
5. **Refuse-to-answer / abstain on low-confidence, don't assert.** Semantic-entropy or PRM-score gating should trigger abstention or explicit low-confidence flagging rather than confident prose, directly answering the competitive gap where DeepWiki asserts wrong claims with full confidence (Section 2, Section 4).
6. **Incremental indexing is a solved problem — don't over-engineer it.** Content-hash + delta re-embed + depth-cutoff placeholders for deep/cold subtrees is documented and cheap; don't budget for full-rebuild costs on a live repo (Section 3).
7. **Orchestrate as an explicit graph (LangGraph-style), not freeform agent chat.** This is both the production-proven default and the pattern with the best available reliability tooling — checkpoints, circuit breakers, HITL nodes (Section 1).

**Risks the research explicitly flags:**

1. **Citation display alone is a trust liability, not a trust asset**, unless backed by an actual verification tier — DeepWiki's citation-adjacent-but-unverified approach is the direct cautionary tale, and it's from the best-funded, most technically credible player in the space (Section 4).
2. **Detector accuracy ceilings (~70-76%) mean "fully verified" claims are false advertising.** Any marketing claiming complete/guaranteed accuracy should be treated skeptically internally before it's said externally; the honest framing is "mechanically gated, not guaranteed" (Section 2).
3. **LLM-as-judge cannot be the sole quality gate** — InstruSum's 40-method null result on summarization-judge alignment is a strong, direct warning against building the verification layer purely on an LLM judge pass (Section 5).
4. **Category mortality risk is real and documented**, not hypothetical — mutable.ai, a credible well-funded entrant in the identical space, quietly died with no pivot or acquisition-for-product. A local-first entrant needs a clear wedge (privacy + verified citation) and a sustainable pricing model decided up front, given Greptile's pricing-instability backlash as the negative comparator (Section 4).
5. **Always-planning agents degrade long-horizon performance.** If the product itself uses an agentic pipeline internally (e.g., an agent-driven summarization/verification loop), don't default to ReAct-style constant planning — use dynamic/adaptive planning compute allocation (Section 1, Section 5's test-time-compute finding).
6. **The single biggest unknown is empirical, not architectural**: no benchmark exists for local 7-14B summarization quality vs. GPT-4-class on real corpora. This must be measured against the target corpus (a repo, a docs folder) before committing to a "fully local" quality claim — budget for this calibration step explicitly (Section 5).
